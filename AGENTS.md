# AGENTS.md

## Цель проекта

Разработать онтологию для построения моделей (цифровых двойников) инженерных систем:

- инженерные системы зданий;
- системы, распределённые по территориям: АСУНО (автоматизированные системы управления наружным освещением), дорожное освещение, энергетика и т.п.

Модель (цифровой двойник) предназначена для:

- построения систем управления и мониторинга;
- отчётности и аналитики;
- учёта (оборудования, активов, ресурсов);
- организации работ по эксплуатации, ремонту, монтажу и модернизации таких систем.

## Язык

- Документация, описания, комментарии — **на русском**.
- Идентификаторы сущностей онтологии (классы, свойства, отношения), имена файлов и код — **на английском**.
- Русские термины предметной области сопровождать английским эквивалентом при первом введении, например: «наружное освещение (street lighting)».

## Принятые решения

- **Целевое хранилище модели — PostgreSQL.** Приложение читает модель (цифровой двойник) из Postgres; это «рантайм»-представление.
- **Формат передачи и версионирования моделей — YAML.** YAML — «исходник» модели: удобен для git, ревью, импорта/экспорта. Направление обмена: YAML → валидация → загрузка в Postgres.
- **Валидация — JSON Schema** (или эквивалентная схема) для YAML-моделей перед загрузкой в БД.
- **OWL/RDF не используем.** Онтология — согласованный словарь понятий (документация + схема), без формального логического вывода и триплет-хранилища. Пересмотреть только при появлении потребности в reasoning или совместимости с отраслевыми онтологиями (Brick, SAREF, BOT, CIM) — по согласованию с пользователем.
- **Согласованное ядро онтологии документировано в `docs/ontology/core.md`.** Черновики и необсуждённые материалы — только в диалоге, в документ не тащить до согласования.

## MVP (первый этап)

Итог первого MVP-этапа:

- модель полностью разложена в **таблицах PostgreSQL**;
- **веб-интерфейс** отрисовывает мнемосхему системы из данных Postgres в согласованной нотации (Device — прямоугольник, Link — линия, Frame — треугольная подпорка, Connector — кружок, Holder — окружность), с интерактивностью;
- **команды устройствам** уходят наружу, **состояния** от устройств принимаются.

Команды и состояния — рантайм-слой поверх модели; ядро онтологии по-прежнему без сигналов и телеметрии (в ядре — только указание наблюдаемого объекта).

## Принцип развития

- **Двигаемся от базы, расширениями функционала.** Сначала — минимальное ядро базовых сущностей; доменные расширения (освещение, энергетика и т.д.) и усложнения добавляются поверх согласованного ядра, по мере необходимости.
- Не проектировать «на будущее»: каждая новая сущность/возможность должна быть обоснована текущей задачей.

## Указания для агента

- **Работа идёт от наработок пользователя.** Пользователь постепенно предоставляет готовые материалы по онтологии; их обсуждаем, частично берём, меняем, переделываем. Не изобретать ядро и структуру с нуля и не забегать вперёд предоставленного материала.
- Это проект моделирования предметной области, а не прикладное приложение. Приоритет — точность и непротиворечивость понятий, прослеживаемость связей, а не скорость написания кода.
- При введении новой сущности онтологии фиксируй: определение (рус.), идентификатор (англ.), связи с существующими сущностями, пример экземпляра.
- Различай уровни: онтология (классы и отношения) ≠ модель конкретной системы (экземпляры) ≠ телеметрия/данные времени выполнения. Не смешивай их в одних сущностях без явного обоснования.
- Учитывай специфику домена: иерархия «территория → объект (здание/участок дороги) → система → подсистема → оборудование → точка учёта/измерения»; пространственная привязка; жизненный цикл актива (монтаж → эксплуатация → ремонт → модернизация → демонтаж).
- Термины АСУНО, наружное освещение, энергетика использовать в общепринятом отраслевом значении; при сомнении — уточнять у пользователя, а не изобретать трактовку.
- Не добавлять инструменты, зависимости и код «на будущее»: репозиторий растёт по мере согласованных решений.
