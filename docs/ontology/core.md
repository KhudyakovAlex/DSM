# Ядро онтологии DSM

Статус: согласованная часть по состоянию на 2026-11-19. Иерархия материальных сущностей: `Unit → Component → Link / Device`.
Черновики, необсуждённые и отложенные материалы в этот документ не входят — они живут в диалоге до согласования.
Проектные решения (хранилище, форматы, MVP, структура репозитория) — в [AGENTS.md](../../AGENTS.md).

## 1. Назначение и границы ядра

Ядро описывает физический состав инженерных систем и движение ресурса: объекты, ресурсные соединения, механические привязки, составность и профили ресурсов. Онтология собственная; маппинг на Brick, CIM, IEC 81346 и другие стандарты — отдельный будущий слой.

**В ядре (текущий состав):**

- материальные сущности Unit; их специализация Component и её специализации Link и Device;
- Resource — профили передаваемого ресурса;
- Holder — точки механической привязки Unit, Connector — точки ресурсного подключения Component;
- ресурсные соединения (пары Connector↔Connector) и механические привязки (пары Holder↔Holder);
- составность объектов, отдельная от наследования классов (§5).

**Не входит в ядро:** сигналы и точки данных, телеметрия, события, работы, участники, документы. Статусы экземпляров и оформление их переходов работами — следующий слой. Функциональные места, классификация/признаки/параметры/требования и соответствие моделей, учёт экземпляров и жизненный цикл — в проработке (см. открытые вопросы).

Уровни не смешивать: онтология (классы и отношения) ≠ модель конкретной системы (экземпляры) ≠ телеметрия/данные времени выполнения.

## 2. Сущности

| Идентификатор | Русское имя | Определение |
|---|---|---|
| `Unit` | Материальная сущность | Физический объект инженерной системы; может иметь крепления для механической связи с другими Unit |
| `Component` | Инженерный компонент | Unit, участвующий в обмене ресурсами через коннекторы; инженерный объект, изделие |
| `Link` | Соединение | Component, пассивно передающий ресурс без изменения его вида |
| `Device` | Устройство | Component, генерирующий, преобразующий, накапливающий, отдающий, коммутирующий или регулирующий ресурс |
| `Resource` | Ресурс | Материальная сущность: конкретный профиль передаваемого, распределяемого или преобразуемого ресурса |
| `Connector` | Разъём | Точка входа, выхода или промежуточного подключения ресурса; принадлежит одному Component |
| `Holder` | Крепление | Физическая деталь или место/зона механического контакта; принадлежит одному Unit |

### Наследование

```text
Unit — материальная сущность, holders[]
└── Component — участник обмена ресурсами, connectors[]
    ├── Link — пассивная передача ресурса
    └── Device — генерация, преобразование, коммутация и другие воздействия на ресурс
```

- Component наследует материальную основу и крепления Unit; Link и Device наследуют их через Component и получают общий механизм коннекторов.
- Link и Device — соседние специализации Component. Device не наследуется от Link: устройство не обязано быть пассивным передатчиком или передавать ресурс от входа к выходу.
- Это классификация одного объекта, а не три вложенных объекта: рубильник одновременно Device, Component и Unit. Отдельный корпус включается в состав только тогда, когда он сам выделен в модели как объект.
- Прежний Frame заменён базовым Unit и не сохраняется как отдельный класс. «Базовый Unit» далее означает Unit без специализации Component; опоры и несущие конструкции — примеры таких объектов, а не весь смысл класса Unit.
- Resource, Connector и Holder описываются отдельно; данная иерархия наследования на них не распространяется.

### Unit

- Материальная основа для всех Component, Link и Device, а также для объектов без функции обмена ресурсами.
- `holders[]`: 0..*; крепления связывают Unit с другими Unit через пары Holder↔Holder.
- Коннекторы вводятся на уровне Component, а не Unit. У базового Unit коннекторов нет; у Link и Device они есть благодаря наследованию от Component.
- Примеры базовых Unit: опора, кронштейн, эстакада, лоток, коллектор для прокладки коммуникаций, DIN-рейка, монтажная панель, фундамент, отдельно учитываемый хомут.
- Пример экземпляра: «Опора 1» с креплением светильника; светильник — отдельный Device, механически связанный с опорой.
- Может быть составным; составность не следует из наследования (§5).
- Функция определяет специализацию: коллектор как строительная конструкция — базовый Unit; коллектор, распределяющий жидкость, — Link, который также является Component и Unit.
- Размещение базового Unit — точка, для протяжённого объекта — трасса. Форма задаётся геометрией соответствующего представления (2D/3D), вне ядра модели.

### Component

- Инженерный объект, изделие, участвующее в обмене ресурсами; общий предок Link и Device.
- Наследует `holders[]`: 0..* от Unit; вводит `connectors[]`: 1..*. Для Link минимальное число коннекторов уточняется до двух.
- Connector имеет единый смысл и правила соединения у всех Component: отдельные классы разъёмов для Link и Device не вводятся.
- Примеры экземпляров через специализации: «Труба подачи воды» — Link; «Вводной рубильник» — Device. Оба — Component с коннекторами и Unit с возможными креплениями.

### Link

- Примеры: провод, кабель, труба, воздуховод, радиоканал, пассивный разветвитель, тройник, прокалывающий зажим.
- `connectors[]`: 2..* (концевые и промежуточные); `holders[]`: 0..* — унаследованные крепления, которые могут отсутствовать.
- Основное представление протяжённого Link — трасса.
- Может включать другие Link, но не Device: многожильный кабель содержит жилы, кабель с отводами — секции (§5).
- Компактные соединители также относятся к Link: определяющим является характер передачи ресурса, а не размер объекта.
- Один Link может проходить через несколько базовых Unit и несколько раз через один базовый Unit, например кабель через опоры.
- Радиоканал считается **материальным каналом передачи** и относится к Link в общей иерархии Unit → Component → Link; наличие твёрдого корпуса или креплений не обязательно.
- Пример экземпляра: «Труба подачи воды» наследует материальную основу и крепления от Unit, коннекторы — от Component, а как Link пассивно передаёт воду между подключениями.

### Device

- Примеры: светильник, драйвер, контроллер, рубильник, автоматический выключатель, насос, датчик, трансформатор тока, генератор, шкаф управления (составной).
- `connectors[]`: 1..* и `holders[]`: 0..* — унаследованные коннекторы и крепления.
- Размещение — точка.
- Может быть составным: внутри — своя схема из Device, Link и базовых Unit, а не просто набор вложенных объектов (§5).
- Пример экземпляра: «Вводной рубильник» наследует материальную основу и крепления от Unit, входной и выходной коннекторы — от Component; включение и отключение передачи ресурса — функция Device, а не наследование от Link. При детализации внутренний путь передачи может быть представлен отдельным Link в составе рубильника.

### Resource

- Полноценная материальная сущность, не справочник-классификатор: насос — Device, труба — Link, разъёмы между ними — Connector, опоры — базовые Unit, вода в трубе — Resource.
- Набор профилей на всю модель; **один экземпляр на профиль**: ливневая вода во всех трубах — одна сущность.
- Примеры профилей: вода, воздух, сжатый воздух, электричество 230В, электричество 10кВ, вода ливневая, канализационные стоки, данные DALI, данные PLC.
- Данные (DALI, PLC) — такой же ресурс ядра; при этом сигналы и телеметрия вне ядра.
- На Resource ссылаются **Connector и Link**.

### Connector и Holder

- Connector принадлежит **ровно одному Component**, в том числе Link или Device; наследование не создаёт дополнительных владельцев или копий разъёма.
- Holder принадлежит **ровно одному Unit**, в том числе Component, Link или Device; возможность иметь крепления общая для всей иерархии, но набор может быть пустым.
- Примеры: «Вход воды» — Connector трубы; «Крепление светильника» — Holder опоры, связанный с парным Holder светильника.
- Позиции коннектора/холдера — слой представления, не ядро модели (см. §6, §9): в логике только факт связи (пара plug), не где она нарисована.

## 3. Связи

- **Наследование** — отношение классов: Component является Unit; Link и Device являются Component. Оно не обозначает физическое включение одного объекта в другой.
- **Ресурсное соединение** — пара `Connector↔Connector` между Component. Всегда пара: на подключениях через Link, на стыках Link и при прямом контакте Device (в модели два коннектора и связь, рисуются слитно).
- **Механическая привязка** — пара `Holder↔Holder`: механический контакт двух Unit, в том числе их специализаций. Наличие отдельной несущей конструкции не обязательно; ресурс через крепление не идёт.
- **Принадлежность порта** — Connector → Component, Holder → Unit; у каждого порта ровно один владелец.
- **Составность** — физическое включение объектов по правилам §5; не наследование и не механическая привязка.
- **Ссылка на ресурс** — Connector → Resource, Link → Resource.

## 4. Различие Device и Link

Общее у Link и Device — материальная основа и крепления Unit, коннекторы Component. Специализацию определяет функция, а не набор портов.

| Признак | Link | Device |
|---|---|---|
| Вид ресурса | Сохраняется | Может преобразовываться |
| Изменение параметров | Только вследствие передачи и потерь | Целенаправленное |
| Генерация ресурса | Нет | Возможна |
| Накопление, коммутация и регулирование | Нет | Возможны |
| Типичное пространственное представление | Трасса | Точка |

- Если объект соответствует обоим описаниям, он относится к **Device**.
- Форма в пространстве — вспомогательный, а не единственный критерий; класс определяет функция.

## 5. Составность и ветвление

Наследование отвечает на вопрос «чем является объект», составность — «из каких объектов он состоит». Возможность иметь внутренние Link не делает Device разновидностью Link. Механическое крепление само по себе не означает включения в состав.

| Составной объект | Допустимые внутренние объекты |
|---|---|
| Базовый Unit (конструкция без специализации Component) | Базовые Unit |
| Link | Link; Device в состав Link не входит |
| Device | Device, Link и базовые Unit |

Правила состава задаются отдельно от наследования: принадлежность всех объектов к Unit не разрешает произвольную вложенность.

- **Составной базовый Unit** — конструкция из других базовых Unit, например опора из отдельных конструктивных частей.
- **Составной Link** содержит другие Link, например кабель — жилы; Device внутри Link не допускается.
- **Составной Device** содержит внутреннюю схему: вложенные Device, Link между ними и базовые Unit (например, монтажную панель); коннекторы составного объекта выводятся на его границу.
- **Вывод на границу** — два варианта: граничный коннектор связан прямой парой с коннектором внутреннего объекта (отдельного Link нет); либо граничный коннектор принадлежит самому составному Device, и от внутреннего объекта к нему идёт внутренний Link.
- **Ветвление Link** моделируется составностью: один общий Link и подлинки-секции внутри него.
- **Стык секций** ставится в точке расхождения направлений (тройник, зажим, муфта): там пары Connector↔Connector концов секций (рисуются слитно).
- **Проходная точка трассы** (изгиб, проход насквозь) — только геометрия, коннектора нет.
- Неразрывная трасса — один Link без внутренних коннекторов.

## 6. Нотация мнемосхем

В этом разделе обозначение **Unit** без уточнения используется для базового Unit, не специализирующегося в Component; Link и Device имеют собственные обозначения. Пунктирная рамка — способ представления базового Unit, не отдельный класс Frame. Унаследованные уровни Unit и Component не рисуются дополнительными объектами вокруг Link или Device.

В реализации используется та же иерархия (§9). Уровни наследования не создают дополнительных размещений: каждый физический объект имеет один ID Unit и одно размещение в конкретном представлении.

- **Device** — прямоугольник с зелёной обводкой.
- **Link** — линия между устройствами (трасса).
- Подписи Device, Link, Unit — цветом обводки соответствующего объекта. Подписи Link не накладываются друг на друга: при пересечении подпись сдвигается по вертикали.
- Схема условная (не вид сбоку): линии земли нет, Unit примыкают к своим Device/Link.
- **Unit** — пунктирный прямоугольник на заднем фоне, охватывающий все его холдеры и подпись (подпись — внутри рамки, у нижней границы); цвет обводки — как у окружностей Holder. Прямоугольник Unit заходит под держимый Device и просвечивает через его полупрозрачную заливку (80% непрозрачности); внутренний Unit составного Device рисуется поверх фона контейнера, но под его устройствами.
- **Connector** — закрашенный кружок: на входе Link в Device и на стыках секций. При переносе и изменении габаритов Device либо правке трассы разъём автоматически переходит на грань со стороны подходящего Link; парный разъём и конец трассы следуют за ним. Прямые контакты Device↔Device и общие граничные разъёмы составных устройств сохраняют своё положение.
- **Holder** — окружность в точке механической привязки.
- Connector и Holder не накладываются друг на друга: у одного владельца разъём и крепление — разные точки (например, ввод по центру грани, крепление у угла).
- Пары в контакте (прямой контакт Device, стык секций, механическое крепление двух объектов) рисуются **слитно**: совпадение позиций выводится из факта соединения, отдельно не хранится. Holder Unit следует за перемещением держимого объекта: его позиция выводится из парного Holder устройства или линка.
- Трассы Link ортогональны (прямые углы). При смещении портов (например, проекция на границу свёрнутого составного Device) трасса перестраивается под прямыми углами с сохранением ориентации сегментов. Линк отходит от края Device прямым участком по нормали к грани («отход»), изгибы трассы — только после отхода от края, не вплотную к нему; на коротких линках отход укорачивается так, чтобы отходы двух концов не перекрывались; на косом коротком линке с параллельными отходами их сумма не превышает расстояния между концами вдоль оси отхода. **Отход направлен наружу грани, а не внутрь тела Device**: трасса у разъёма не заходит внутрь прямоугольника устройства; после переносов, ресайза и правки сегментов вершина трассы у конца, подключённого к разъёму Device, удерживается снаружи по нормали грани (не ближе защитного отхода). Угол перегиба у грани Device едет за концом трассы: сегмент, примыкающий к девайсу, смещается вместе с ним целиком, а следующий за углом сегмент удлиняется/укорачивается; «хвост» трассы на старом месте не остаётся. На стыке секций отход направлен вдоль прилегающего участка трассы, без обратного выступа. При параллельных отходах и смещённых концах добавляются два прямых угла; коллинеарные возвраты удаляются, чтобы не оставалось «аппендиксов». После переноса концы трассы совмещаются со своими коннекторами, в том числе на общем стыке секций.
- Клик по элементу (в том числе по его подписи) выделяет его: остальные элементы приглушаются; сброс — клик по пустому месту или Esc. Мнемосхема занимает всю свободную область страницы и при открытии встаёт в её центр. Поле бесконечное (расширяемое полотно с пустыми полями вокруг содержимого); драг за пустое место — панорамирование по полю; при выходе содержимого за край области появляются прокрутки. Масштаб компонентов фиксированный (1 единица модели = zoom px), авто-подгонки под контейнер нет и при редактировании масштаб не меняется; зум — кнопками «+»/«−» рядом с карандашом и колесом мыши с зажатым Ctrl (зум в точку курсора и из неё); без Ctrl колесо — обычная прокрутка.
- Режим редактирования включается кнопкой-карандашом; в этом режиме на фоне — контрастная **точечная** сетка в координатах модели (масштабируется и панорамируется вместе со схемой); шаг сетки настраивается полем рядом с кнопками зума. При перетаскивании элементов действует магнит к сетке: у Device снапится левый верхний угол, у Unit — вершина; во время драга снапится смещение от старта (объект не прыгает сам по себе и не отстаёт), точная посадка угла на сетку — при отпускании. Перенос распространяется на всё, связанное с объектом парами Holder↔Holder (Unit, Device, Link) и каскадом Connector↔Connector: связи не рвутся. Габариты Device меняются перетаскиванием за правый нижний угол (ручка ресайза видна только в режиме редактирования); якорь — левый верхний угол, порты и крепления масштабируются пропорционально, парные коннекторы линков следуют каскадом; габарит сохраняется в слое представления PostgreSQL. В режиме редактирования Device перетаскивается мышью, вместе с ним едут его коннекторы, крепления и внутренняя схема составного Device; парные коннекторы линков следуют за контактом, трассы перестраиваются ортогонально, Unit — за креплениями. Unit также перетаскивается: вместе с ним едет всё закреплённое на нём через пары Holder↔Holder — Device со своей внутренней схемой и каскадом контактов, Link жёстко со своей трассой; стык секций и соседние секции следуют за перемещённым концом трассы. Крепления линка едут за трассой: точка привязки сохраняется на своём сегменте и после перестройки остаётся на линии. После отпускания мыши правка раскладки автоматически сохраняется в PostgreSQL (`placement`): позиции и габариты Device, размещение Unit, позиции Connector/Holder и трассы Link записываются одной транзакцией. Сохраняются только изменённые размещения, включая правки на внутренних полях; относительные системы координат сохраняются. Интерфейс показывает состояние сохранения; при ошибке правки остаются в памяти, доступен повтор сохранения, а уход со страницы с несохранёнными изменениями вызывает предупреждение. Логические сущности, связи и YAML-исходник модели не изменяются. Захват за кружок Connector/Holder перемещает объект-владельца порта; при переносе конца трассы вместе с коннектором едет и соседняя вершина (угол у грани), контакт не отрывается.
- Пересечения трасс без коннектора — не соединения.
- **Правка трассы Link** (режим редактирования): внутренние сегменты трассы перетаскиваются мышью — горизонтальные по вертикали, вертикальные по горизонтали; координата сегмента магнитится к сетке. У каждого разъёма сохраняется **защитный отход**: линк выходит из Device/стыка перпендикулярно грани на фиксированное расстояние. Сегмент, примыкающий к отходу, скользит стыком по оси отхода (отход не короче защитного расстояния); сегмент, лежащий с отходом на одной оси, поперёк не двигается. Дальше соседнего угла перегиба сегмент не едет — примыкающий сегмент не разворачивается назад, излом не образуется. Все сегменты остаются под прямым углом, концы трассы (коннекторы) не смещаются; крепления линка следуют за трассой.
- **Составной Device**: в режиме просмотра свёрнутый — прямоугольник того же размера, что соседние Device того же уровня, с кнопкой «+/−» внутри; клик по кнопке анимированно разворачивает/сворачивает внутреннюю схему. Внутреннее содержимое проявляется только во второй половине анимации и не остаётся поверх свёрнутого контейнера. Развёрнутый — прямоугольник-контейнер с внутренней схемой. В режиме редактирования составные Device на общем поле всегда свёрнуты; вместо «+/−» — кнопка-карандаш, открывающая отдельное поле внутренностей выбранного Device. На этом поле видны его граница, граничные коннекторы и внутренние Device, Link, Unit; внешняя схема отсутствует. Граница родителя не перетаскивается, но её размер меняется ручкой-квадратом в правом нижнем углу; якорь — левый верхний угол. Этот габарит используется при раскрытии Device в режиме просмотра. При переносе отдельного внутреннего Device его соседи не перемещаются через общий Unit: парное крепление Unit следует за устройством, контур Unit охватывает новые позиции креплений. Прямой перенос самого Unit по-прежнему перемещает закреплённые на нём объекты. Вложенный составной Device также редактируется на своём поле через карандаш. Кнопка «Назад» возвращает на предыдущее поле с сохранением масштаба и положения прокрутки; завершение редактирования возвращает на общую мнемосхему. Правка начинки не перемещает внешние объекты.
- В раскрытом режиме граничный коннектор с прямой парой к внутреннему коннектору не рисуется (проходная точка): внешний Link дотягивается до внутреннего коннектора. Граничный коннектор, принадлежащий самому составному Device, рисуется на периметре; к нему подходит внутренний Link.
- Нотация машинная: схемы рисуются из данных PostgreSQL в веб-интерфейсе (MVP). Размещение (точка/трасса) и позиции портов хранятся в слое представления, не в ядре модели (см. §9). Координаты внутренних Device, Unit и трасс Link — относительно родителя; начало координат внутреннего поля — центр составного Device. Connector устройства и Holder устройства/базового Unit размещаются относительно своего владельца; порты Link — в той же системе координат, что его трасса. Секции Link наследуют систему координат составного Link. При переносе составного Device относительные координаты начинки не меняются, весь состав перемещается с родителем.
- Интерфейс и схема — в тёмной теме (`color-scheme: dark`): тёмные фон, карточки и кнопка; цвета нотации сохраняются (зелёный Device, голубой Link, янтарный Holder/Unit).

## 7. Уровни детализации (LOD)

- **LOD (Level of Detail, уровень детализации)** — шкала, которой измеряем и отделяем уровни детализации модели (цифрового двойника): насколько подробно описаны состав, связи, параметры и поведение системы. Идентификатор: `LOD`; значения — числовая шкала (LOD100, LOD200, …).
- LOD характеризует модель или её фрагмент, а не отдельную сущность: это мера полноты описания, а не новый класс объектов.
- **Текущий этап — LOD100, нижний уровень.** В него входит всё согласованное ядро: физический состав (Unit и его специализации Component → Link / Device), ресурсные соединения и механические привязки, составность, профили Resource; условная геометрия размещения для мнемосхемы (точка/трасса, позиции портов) — в слое представления, не в ядре модели. Вне LOD100: физические параметры и характеристики, сигналы и телеметрия, учёт экземпляров и жизненный цикл, работы и участники.
- Словарь LOD100 задаёт ядро онтологии (§2–§5), нотация мнемосхем (§6) — его визуальное представление. Повышение LOD — последующие слои (рантайм команды/состояния, параметры, учёт); каждое расширение обосновывается текущей задачей.
- Пример уровня детализации: учебная модель (`db/init.sql`) — LOD100; хранение наследования, связей и размещений описано в §9.
- Состав уровней выше LOD100 и механизм маркировки (модель целиком, фрагмент, элемент) — не согласованы (см. §8).

## 9. Соответствие учебной схеме

Учебная схема (Docker-стенд): `db/init.sql`, `db/schema.dbml`. Наследование хранится через отдельные таблицы классов с общим первичным ключом (class-table inheritance), а не через PostgreSQL `INHERITS`.

Логические таблицы (без координат): `unit`, `component`, `device`, `link`, `resource`, `connector`, `holder`, `connector_plug`, `holder_plug`.

| Понятие | Хранение |
|---|---|
| Unit | `unit(id, name, kind, parent_id)` — все физические объекты, общий ID и название |
| Базовый Unit | Строка `unit` с `kind = 'unit'`, без строки Component |
| Component | `component(id)`; первичный ключ одновременно ссылается на `unit.id` |
| Device | `device(id)`; первичный ключ ссылается на `component.id`, `unit.kind = 'device'` |
| Link | `link(id, resource_id)`; первичный ключ ссылается на `component.id`, `unit.kind = 'link'` |
| Connector | `connector.component_id` — обязательный единственный владелец Component |
| Holder | `holder.unit_id` — обязательный единственный владелец Unit |
| Составность | `unit.parent_id` — непосредственный родитель, независимо от уровня наследования |

В текущем хранении Component представлен через специализации Device и Link. Строки нескольких таблиц описывают один объект с одним ID, а не отдельные объекты в составе. Ограничения БД проверяют соответствие `kind` строкам специализаций, отсутствие одновременно Device и Link, допустимость состава и отсутствие циклов. Составность не кодируется связью первичных ключей классов. Проверки специализаций отложены до завершения транзакции; изменения графа сериализуются общей advisory-блокировкой и выполняются при `READ COMMITTED`, `TRUNCATE` этих таблиц запрещён.

`GET /api/model` возвращает все физические объекты в `units` с `kind` и `parent_id`, коннекторы с `component_id`, крепления с `unit_id`; точки трасс Link ссылаются на тот же ID Unit. Клиент группирует физические объекты по конкретному виду для отрисовки, не дублируя объекты по уровням наследования. `PUT /api/entities/:type/:id` редактирует имя, а для Link — также ресурс; имя Device и Link хранится в `unit`, ресурс Link — в `link`. Обновление имени и ресурса выполняется одной транзакцией.

Слой представления: `view` (реестр представлений; текущая мнемосхема 2D — одно из них, позже 3D и пр.) и `placement` (универсальная таблица размещения: вид + тип сущности + id + геометрия в jsonb — точка, габарит, трасса, позиции портов). Для всех физических объектов `placement.entity_type = 'unit'`, `entity_id = unit.id`; для портов — `connector` и `holder`. Геометрия определяется конкретным видом Unit: Device — `x/y/w/h`, базовый Unit — `x/y/base_y`, Link — `lines`. API сохранения проверяет геометрию по виду объекта из БД, а не только по типу размещения. Добавление нового представления не меняет логическую схему БД: новые записи в `view` и `placement`.
Пример: ТП — составной шкаф (автомат, счётчик, контроллер, контактор на монтажной панели) — два светильника на опорах; демонстрирует оба варианта вывода на границу (§5).
Стенд: `db/docker-compose.yml` — PostgreSQL 16 (localhost:5433, пользователь/пароль/база `dsm`) и веб-интерфейс (localhost:8080). Пересборка веба после правок: `docker compose up -d --build web` из каталога `db/`; `init.sql` применяется только к пустому тому. Сервер отдаёт статику и `/api/model` с `Cache-Control: no-store`, чтобы браузер не кэшировал устаревшие файлы. `PUT /api/placements` принимает изменённые размещения мнемосхемы 2D, проверяет геометрию и существование сущностей и сохраняет весь набор атомарно в `placement`.

Переход с прежней схемы Device / Link / Frame выполняется однократно скриптом `db/migrate-unit-component.sql` после резервного копирования и проверки на копии БД. Скрипт переносит существующие объекты и владельцев портов в общую иерархию, заменяет ссылки размещений, сохраняет геометрию и пары контактов; старые таблицы и поля удаляются только после переноса и проверок в той же транзакции. Повторно инициализировать данные или удалять том PostgreSQL для миграции не нужно.

Проверки выполняются на отдельной тестовой БД и сервере:

- `docker exec -i dsm-db psql -U dsm -d <test_database> -v ON_ERROR_STOP=1 < db/test-unit-component.sql` — ограничения наследования, состава и владельцев; тестовые строки откатываются.
- `TEST_BASE_URL=http://localhost:8081 node --test web/server.test.js` — новый формат API, сохранение размещений и свойств, откат при ошибках и проверка входных данных. Сервер на этом адресе должен быть подключён к тестовой, а не рабочей БД.
